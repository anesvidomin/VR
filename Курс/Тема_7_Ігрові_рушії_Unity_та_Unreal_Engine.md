# Тема 7. Ігрові рушії Unity та Unreal Engine

## 1. Навіщо будівельнику ігровий рушій

**Ігровий рушій** — середовище для створення програм із тривимірною графікою в реальному часі. Історично рушії створювалися для ігор, але сьогодні їх використовують в архітектурі, машинобудуванні, кіно, навчанні та тренажерах.

Візуалізатори (Enscape, Twinmotion) вирішують одну задачу — показати модель. Ігровий рушій потрібен тоді, коли задача ширша.

**Що дає рушій і чого не дає візуалізатор:**
- **інтерактивність** — користувач може натискати, брати, перемикати, відчиняти;
- **сценарії** — послідовність подій: виконай дію, отримай результат, помилися, отримай наслідок;
- **власний застосунок** — готовий файл, який встановлюється на шолом і працює без ліцензій і без материнської програми;
- **власна логіка** — підрахунок балів, фіксація дій користувача, перевірка правильності виконання;
- **нестандартні інструменти** — вимірювання, розрізи, порівняння варіантів, накладання «проєкт–факт».

**Типові приклади в будівництві:**
- тренажер з охорони праці зі сценарієм і оцінюванням;
- конфігуратор оздоблення: замовник сам перемикає матеріали й бачить результат;
- тренажер монтажу вузла: елементи треба зібрати у правильній послідовності;
- інтерактивна презентація об'єкта з перемиканням розділів моделі.

**Два рушії.** Unity й Unreal Engine покривають практично весь ринок. Unity вважається простішим для початку та краще пристосованим до автономних шоломів. Unreal Engine дає кращу картинку «з коробки» й має надбудову Twinmotion, орієнтовану саме на архітекторів.

## 2. Будова сцени

Незалежно від рушія, логіка однакова.

**Сцена (Scene / Level)** — віртуальний простір, у якому розміщені всі об'єкти. Проєкт може містити кілька сцен: наприклад, меню, перший поверх, майданчик.

**Об'єкти.** Усе, що є у сцені — модель будівлі, джерело світла, камера, точка старту користувача. Об'єкти утворюють **ієрархію**: якщо вікно підпорядковане стіні, то при переміщенні стіни воно рухається разом із нею.

**Компоненти.** До кожного об'єкта додаються властивості: геометрія, матеріал, фізичне тіло, колайдер (невидима форма, що відповідає за зіткнення), скрипт поведінки. Саме колайдер не дає користувачу пройти крізь стіну.

**Матеріали.** У рушіях застосовується підхід PBR (фізично коректне відображення): матеріал описується набором карт — базовий колір, шорсткість, металевість, нормалі (рельєф). Після імпорту моделі з BIM-програми матеріали майже завжди доводиться налаштовувати заново.

**Освітлення.** Джерела світла: напрямлене (сонце), точкове (лампа), прожектор, площинне. Для архітектурних сцен освітлення зазвичай запікають у текстури, щоб не витрачати продуктивність.

**Камера й точка старту.** Визначають, звідки користувач починає огляд. Для VR камера прив'язується до положення шолома.

## 3. Імпорт моделі з BIM-програми

**Послідовність:**
1. У Revit / ArchiCAD / SketchUp підготувати модель: прибрати зайве, спростити (див. тему 5).
2. Експортувати у FBX (найчастіше) або glTF.
3. Імпортувати файл у рушій.
4. Перевірити масштаб, орієнтацію та положення.
5. Призначити матеріали заново.
6. Додати колайдери на підлогу й стіни.
7. Налаштувати освітлення.

**Типові помилки:**

*Неправильний масштаб.* Модель у 100 разів більша або менша за потрібну. Причина — різні одиниці вимірювання. У Unity одна одиниця дорівнює одному метру; перевіряти масштаб слід одразу, поставивши поруч об'єкт відомого розміру — наприклад, фігуру людини заввишки 1,75 м.

*Модель далеко від початку координат.* Якщо у проєкті використовувалися геодезичні координати, модель після імпорту може опинитися за кілометри від центру сцени. Наслідок — тремтіння зображення через похибки обчислень. Перед експортом модель переносять у початок координат.

*Перевернута модель.* У різних програмах вертикальною віссю вважається Y або Z. Виправляється поворотом на 90° після імпорту.

*Чорна або біла модель.* Матеріали не перенеслися — їх треба призначити вручну.

*Низька продуктивність.* Модель не була спрощена перед експортом.

## 4. Unity

**Інтерфейс:** вікно сцени, ієрархія об'єктів, інспектор властивостей вибраного об'єкта, вікно проєкту з файлами.

**XR Interaction Toolkit** — офіційний набір компонентів Unity для віртуальної реальності. Головне: він містить **готові шаблони**, які дозволяють отримати працюючу VR-сцену без написання коду.

Що дає набір:
- **XR Origin** — «гравець»: камера, прив'язана до шолома, і два контролери;
- **телепортація** — переміщення у вказану точку, базовий спосіб руху, що не викликає кіберхвороби;
- **плавний рух і поворот ривками** — альтернативні способи переміщення;
- **захоплення об'єктів** (Grab Interactable) — достатньо додати компонент до об'єкта, щоб його можна було взяти в руки;
- **взаємодія з інтерфейсом** — віртуальні кнопки, перемикачі, панелі;
- **променевий вказівник** — вибір об'єктів на відстані.

**Порядок створення базової VR-сцени:**
1. Створити проєкт (шаблон 3D або VR).
2. Підключити модулі XR Plugin Management і XR Interaction Toolkit, увімкнути підтримку OpenXR.
3. Додати у сцену XR Origin.
4. Імпортувати модель будівлі, налаштувати масштаб і матеріали.
5. Додати колайдери та область телепортації на підлогу.
6. Налаштувати освітлення.
7. Перевірити роботу через підключений шолом.

**OpenXR** — відкритий стандарт, завдяки якому один застосунок працює з різними шоломами (Quest, Vive, Index) без переробки.

## 5. Unreal Engine і Twinmotion

**Unreal Engine** дає вищу якість зображення без додаткових налаштувань і має **VR Template** — готовий проєкт, у якому вже реалізовані телепортація, захоплення об'єктів і взаємодія з інтерфейсом.

Особливість Unreal — **Blueprints**: візуальне програмування. Логіка складається зі з'єднаних блоків замість написання коду. Для будівельника без досвіду програмування це суттєво простіший шлях.

**Datasmith** — технологія імпорту даних із CAD- і BIM-програм (Revit, ArchiCAD, SketchUp, 3ds Max) в Unreal зі збереженням структури моделі та матеріалів. Значно якісніша за звичайний експорт у FBX.

**Twinmotion** побудований на Unreal Engine, але спрощений до рівня архітектора: немає програмування, є бібліотеки, матеріали, оточення, погода, рослинність, людина, транспорт. VR-режим вмикається однією кнопкою.

**Коли чого достатньо:**
- потрібно показати модель у шоломі з гарною картинкою → **Twinmotion**;
- потрібна інтерактивність, сценарій, власний застосунок → **Unreal Engine** або **Unity**;
- цільовий пристрій — автономний Quest без комп'ютера → частіше **Unity** (простіша оптимізація під мобільний процесор).

## 6. Складання та запуск застосунку

**Режим із підключенням до комп'ютера.** Шолом підключається кабелем (Quest Link) або через Wi-Fi (Air Link) і працює як монітор. Обчислення виконує комп'ютер. Це основний режим для роботи з важкими моделями та під час розробки — результат видно одразу, без складання застосунку.

**Автономний режим.** Застосунок збирається у файл **APK** і встановлюється безпосередньо на шолом. Працює без комп'ютера. Такий файл можна передати замовнику або на будмайданчик.

**Порядок складання під Quest 3 (Unity):**
1. Перемкнути платформу проєкту на Android.
2. Увімкнути підтримку OpenXR і профіль Meta Quest.
3. Увімкнути режим розробника на шоломі через обліковий запис Meta.
4. Підключити шолом кабелем, дозволити налагодження по USB.
5. Виконати Build and Run — застосунок збереться й запуститься на пристрої.

**Типові проблеми:** шолом не визначається (не ввімкнено режим розробника або не підтверджено дозвіл на USB-налагодження всередині шолома); застосунок запускається й одразу закривається (помилка в налаштуваннях графіки); низька частота кадрів (модель не оптимізована під мобільний процесор).

**Тестування.** Перевіряти слід не лише на комп'ютері, а обов'язково у шоломі: контролювати частоту кадрів, зручність переміщення, досяжність елементів, відсутність провалів крізь підлогу.
